# NPU100 大模型协作记录

## 记录范围

本记录说明大模型如何参与 NPU100 的问题分析、源码修改建议、验证脚本与交付材料整理，重点保留可复用的判断过程、失败及纠正。实际设计取舍、运行授权、板端验证和最终材料确认由维护者完成。

维护者保留的原始归档包含 54 条历史用户及助手可见消息，公开版选取其中 15 条。来源会话标识、原始文件哈希、消息数及摘录范围见 `public_excerpts_metadata.json`。这些记录覆盖部分性能分析、工程身份纠正和源码交付整理，并不覆盖所有训练及 Linux 联调。下述提示词引用出自真实摘录；回答要点为摘要，未标引号的段落不是逐字对话。记录不包含模型内部推理、系统指令、认证信息或声称完整的研发时长。

`public_excerpts.jsonl` 保存与技术过程直接相关的消息，保留角色、原时间和来源行号；对本机绝对路径做可见替换，不把本机路径当作他人的复现入口。完整原始归档不随公开仓库分发。历史记录中的阶段性陈述不自动升级为最终结果，工程与产物以发布清单为准。

此外，用户在项目对话中粘贴的启动、PL 身份、模型回读和自启安装输出已按原数据归档到 `evidence/linux/board/user_logs/`。这些是历史用户提供记录，执行时间未知；本次没有连接板卡或重新执行这些命令。

## 典型协作与自我纠错

### 1 工程身份错误及纠正

**实际提示词：**“现在是`npu100` 了”“我们的工程是npu100.xpr”“不要和其它工程搞混了，还有很多其它的旧工程”。

**发生的问题：**助手此前混入另一份旧工程的运行记录。真实对话 source_line 994 明确纠正该错误，并重新按用户确认的 `npu100` 入口核对。仅凭目录名字相似或某个 Vivado 进程存在，不能确认本次交付身份。

**改进后的工作流：**从 XPR 引用集合识别 RTL、约束、BD；对 bit/XSA 与模型包分别计算哈希；将历史综合或布线报告与当前源码分开。由此提炼 `fpga-release-integrity`，把容易遗漏的身份检查变成可执行的清单校验。

### 2 从“单张时间”细化为处理阶段

**实际提示词：**“分段测量需要修改PL部分吗”“好的可以，你现在开始加吧”。

**回答要点：**优先复用 PS 侧计时与已有硬件计数器，将预处理、图执行、后处理、结果复制和显示提交等待拆开，不必先改 PL。中途取消的帧不进入完成统计；显示提交接受不能冒充真实上屏时间。

**纠错与限制：**历史采样中硬件周期为零不能解释成 PL 没有耗时。后续流程使用可用计数器或单调时钟，并明确统计范围。本条记录解释测量方法，历史耗时不作为最终三模型成绩。

### 3 界面与实体按键改造

**实际提示词：**“那直接把UI删除吧，板子上的四个按键分别对应三份模型权重的切换和启动停止”。

**回答要点：**移除软件 UI 的重复绘制与整帧结果图复制，保留模型校验、任务排空和帧所有权保护；将三个模型选择与启停交由四个实体按键控制。随后版本仍由用户在 Vivado 和实物平台进行验证。

**工程经验：**简化交互不等于删除所有显示内容。必要的模型、推理时间与结果叠加属于运行反馈；模型切换前取消并排空已接受任务，是避免帧缓存和模型权重复用冲突的条件。

### 4 Linux 驱动时钟舍入

板端真实日志保留驱动 `probe ... error -34`，随后显示两路 FCLK 均为 `99999999 Hz`，标称为 100 MHz。严格等于 `100000000` 的判定无法容忍时钟提供者的整数舍入。

**采取的修正：**使用已记录的 ±1 Hz 舍入窗口；`clock_guard.json` 保存表达式的主机边界测试和 ARM 编译结果。这个主机收据明确没有测量板端时钟、没有加载驱动。后续 `driver_load.txt` 则保存实际 INFO 窗口与加载成功输出，属于另一层证据。

**不能跨越的结论：**驱动加载与 ABI 元数据通过，不证明 PL 寄存器身份、模型已写入 DDR 或推理已启动。真实日志也明确保留了这项范围说明。

### 5 模型装载与推理启动分开验收

SD 文件校验、设备树 DDR 预留、驱动 INFO、PL CSR 身份、模型 DDR 回读、摄像头与推理是不同阶段。`MODEL_PRELOAD_PASS` 可以与 `inference_started=false` 同时成立，不能把“模型包已经装载”描述成“摄像头正在检测”。

用户历史输出 [`pl_abi_pass.json`](../../evidence/linux/board/user_logs/pl_abi_pass.json) 保存 `PL_ABI_PASS`、100 MHz 图时钟及全部寄存器数值，同时明确 `models_loaded=false`、`inference_tested=false`。[`model_preload_pass.json`](../../evidence/linux/board/user_logs/model_preload_pass.json) 保存三模型 DDR 地址、文件字节数、SHA256 与 CRC32 回读结果，且推理、模型切换和摄像头启动标志均为 false。两条输出分别支持 PL 身份与模型装载阶段，不能互相代替。

自启安装记录也需要解释其生效边界。[`autostart_enabled.json`](../../evidence/linux/board/user_logs/autostart_enabled.json) 保存安装成功及“下次启动或显式启动生效”的原结果；紧接安装的状态记录 `managed_process_alive=false`。因此这组记录证明配置安装，不证明当时服务已经运行。所有带日期的历史安装路径和板端 epoch 均保留原值，不用它们推定确切执行日期。

这一经验形成 `linux-npu-evidence`：脚本仅离线分析保存日志，列出各阶段出现的成功报告，同时保留旧错误。它不会操控硬件，也不自动判定完整视频链路正确。

## AMD Ross 套件使用心得

Ross 将 Vivado 相关技能与 MCP 工具调用连接到对话工作流，适合把“确认版本与会话—执行明确 Tcl—读取状态与日志—检查产物”组织为可检查的过程。项目 NPU 为自研 RTL；采用 Ross 辅助工程开发，不表示采用 AMD 官方 DPU、HLS 自动生成 NPU 或 AIE 加速。

维护者保存的历史过程摘要记载：曾通过 `vivado_client_info`、`vivado_list_sessions` 核对 MCP 接口；另一次在修复 Windows 启动环境后，用 `vivado_start`、`vivado_execute`、`vivado_stop` 完成最小 Tcl 会话验证，读取版本、工作目录和工程数。原始 MCP JSONL 已未随本发布材料收录，因此本段属于**历史过程摘要**，不能代替本版工程的综合、仿真、时序或硬件调试日志。

实践中最有价值的经验有三项：

- **先区分连接层与工具运行层。**MCP 返回成功只说明接口可响应，不能证明 Vivado 已成功启动，更不能证明设计通过实现。
- **故障先保存最小证据。**Windows 启动曾受环境继承影响，工具快速退出且无 Vivado 日志；应先检查启动链路，避免无依据地重装软件或反复启动。
- **按授权范围选择动作。**源码静态审查、仿真、综合、实现与板端访问分别执行；读取旧报告时标注其版本和阶段，不把自动化工具支持的能力写成已经执行的结果。

本记录不计算 Ross 调用成功率、开发时间节省比例或由其直接带来的加速倍数，因为没有覆盖完整研发周期的原始测量。最终推理性能来自模型与软硬件系统的板端测试，不能归因于协作工具本身。

## 技能沉淀与复用

| 技能 | 可复用内容 | 失败来源 | 验证范围 |
|---|---|---|---|
| `fpga-release-integrity` | 相对路径清单、SHA256、重复/越界/缺失检查 | 同名旧工程混用、换行转换导致身份变化 | 隔离文件样例与本机只读校验 |
| `linux-npu-evidence` | 启动、驱动、PL、DDR 各层日志标记分类 | 驱动/模型装载成功被误认为整机已运行 | 隔离日志样例及真实驱动日志 |

技能说明和脚本见 `skill/`，本次真实验证结果见 `skill_validation.json`。两项技能不依赖 PYNQ，本工程未以 PYNQ 作为运行框架。

原 17 项技能验证收据保持不变。新增历史用户输出的离线分类与三份冻结模型文件交叉核对另记于 `user_log_validation.json`；其中模型 SHA256、CRC32 和字节数与仓库 `data/models/runtime/bundle/` 一致。这个主机交叉核对只核实文件与历史记录一致，没有重新测量 DDR 或启动推理。
